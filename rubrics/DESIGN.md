# DESIGN — 个人评价体系的 taxonomy 与演进循环

## 1. 评价本体（一条标准长什么样）

每条标准记三件东西：判断、情境、动机。

**判断**

- 强度：`veto`（一票否决）/ `must`（要求）/ `prefer`（偏好）/ `penalty`（扣分）
- 判据形态：`mechanical`（可写成检查条件）或 `heuristic`（需人判断的主观地带）
- 正例 / 反例：我实际说过"好/不好"的实例，标准会漂移，实例不会

**情境（五根正交轴，取值开放，遇新扩新）**

- `object`：对象 —— 模型/系统、数据、方法、结果、写作、工具流程、人/合作、产品
- `decision`：决策类型 —— 要不要做 / 选哪个 / 信不信结果 / 何时停 / 怎么表达 / 交给谁
- `state`：对象状态 —— 未开始 / 已运行 / 结果已出 / 出现冲突 / 要交付 / 复盘
- `constraints`：环境与约束 —— 预算、可复现性、受众、是否发表、时间尺度
- `trigger`：触发信号 —— 什么证据出现才激活（如"提升被归因于 X 但无消融"）

**动机（"出于什么"，四个可分开记录的东西）**

- `goal`：当下目标 —— 发论文 / 落地 / 学懂 / 建长期能力
- `value`：跨任务稳定的原则 —— 诚实报告负面、可复现优先、成本意识、复杂度留给系统
- `cost`：代价记忆 —— 踩过的坑（负面标准的主要来源）
- `role`：角色 —— 研究者 / 工程 owner / 学习者 / 产品负责人

## 2. 为什么这样拆

- 阶段/事务/状态不是三根轴，而是对象、决策类型、对象状态三根不同轴 —— 混在一起会让
  匹配失效。
- "决策类型"比"阶段"更本质：同一件事，在"要不要做"和"信不信结果"两种决策下，
  标准完全不同。
- 角色会影响标准：同一个人换角色，评价可能反转（受 Separating Memory and Workflow
  Effects 启发——记忆与工作流效应要分开）。
- 归因意识（trigger 轴）来自 PACT / Groupwise Agentic Grading：很多负面标准其实是
  "这个提升没证明来自它声称的机制"。

## 3. 演进循环（RSI 式）

本项目的核心：**用自己产出的情境匹配来改进自己**。

```
观察 Observe    从新素材（对话判断、归档选择、备注、cookbook 分歧）提取候选标准
   ↓
提出 Propose    生成「候选条目 + 它的情境 + 正反例」，放进 proposals/
   ↓
验证 Verify      我确认/修正/否决；系统统计「我改了多少」作为自我改进信号
   ↓
沉淀 Sediment    确认的条目进 seed/，被否决的连同情境写进沿革（为什么在那个情境下不成立）
   ↓
回看 Reflect     定期检查：哪些轴取值过多、哪些标准总被推翻、taxonomy 要不要改
```

每一轮都只**增、收窄、切分**，不删除。taxonomy 本身也版本化（见 notes/evolution-log.md）。

## 4. 和主仓库其它功能的边界

- cookbook（最佳实践/）存的是"论文结论在什么条件下成立"；rubrics 存的是
  "我的标准在什么情境下成立"；两者可互相引用（某条标准的 `value/cost` 可链到某篇论文），
  但**代码与存储不共享**。
