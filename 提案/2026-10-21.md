## P1. 单面记忆写入：是否入库交给可重放验证器

- **要解决的问题**：他把记忆写什么、是否入库、什么时候触发混在一次生成里，模型容易把一次失败写成长期规则，之后换任务仍继续误用。
- **假设**：如果写入端只产生“条件→动作→证据”的单面条目，再由独立、可重放的验证器决定入库或退回，那么错误记忆率和误触发都会下降，同时不牺牲长任务成功率。
- **做法**：写入器不判断好坏，只输出触发条件、候选动作和来源轨迹片段；验证器重建对应环境前缀，执行该动作并检查结果，返回接受、修正、隔离三档。隔离条目不能直接进入上下文，只能在之后的新轨迹中再次获得证据。
- **最小实验**：1–2周：在ALFWorld与ScienceWorld各取120个任务，固定Qwen3-8B和同一harness，比较不留记忆、模型自判并总结、单面写入加可重放验证器三组；每组2个随机种子，按held-out任务和相同token预算评测。
- **指标**：held-out任务成功率、错误入库率、触发条件精确率、每任务注入token数。
- **判负条件**：如果验证器组相比模型自判组成功率没有提高至少2个百分点，或错误入库率下降但held-out成功率反而下降，就说明这个写入闸门不成立。
- **风险 / 与已有工作**：真实环境常常不能重建前缀，验证器和写入器同模型时还可能互相背书；相对已有工作的增量必须落在“写入端不自我批准、验证可重放”这一点上。
- **证据**：EVISKILL: Grounding Skill Evolution in Replayable Evidence · Context Evolution (ACE) vs. Runtime Intervention (AgentGuard) · Relevance Does Not Imply Applicability: Experience Activation for Personal GUI Agents · Learn2Play Bench: How Well Do LLM Agents Learn from Experience in Unfamiliar Environments?
- **来自你的灵感**：记忆模块能不能只写一个面，让验证器来判 · memory这里现在其实还是没找到一个机器能懂的语言或者组织形式，很多时候还是对齐做的差，trigger / condition 不清楚，有时候原文都更管用了。

## P2. 把“原文更管用”做成证据指针记忆

- **要解决的问题**：摘要式记忆会丢掉文件路径、标识符、否定条件等后续关键细节，模型不知道何时该相信摘要、何时必须重新读原文。
- **假设**：记忆同时保存结论和不可变证据指针，并按任务所需精确度选择回读原文或只用摘要，能在同样上下文预算下提高事实准确性和跨轮任务成功率。
- **做法**：每条记忆拆成结论、适用条件、证据指针和原始证据哈希；运行时先判断任务是否存在代码修改、字段值、引用、时间等“精确匹配需求”，命中时回读原始片段，否则使用压缩结论。指针失效或原文版本变化时自动把条目降级为待核验。
- **最小实验**：1–2周：构造120个混合任务，覆盖代码修复、日志查询、文档问答和配置修改；比较纯摘要、只存指针、结论加指针三种记忆，固定Qwen3-8B、上下文预算和工具权限。
- **指标**：任务成功率、关键字段完全匹配率、引用错误的次数、平均token成本、原文重读率。
- **判负条件**：如果结论加指针组在相同预算下没有比纯摘要组更准，或为了保持准确性所需的token超过摘要组1.5倍，就说明回读策略不划算。
- **风险 / 与已有工作**：这和JIT Memory的读时整理接近，增量在于把“何时必须看原文”显式化；如果原环境和文件版本无法可靠固化，指针会失效。
- **证据**：Just-in-Time Memory: Learning to Curate Task-Adaptive Memory for LLM Agents · Pack Light, CarryOn: Building Object-Oriented Context for Long-Horizon Agents · Skip the Compressor: Coding Agents Fix More Issues When They Pick Whole Files · Latent Compaction with Test-Time Training
- **来自你的灵感**：memory这里现在其实还是没找到一个机器能懂的语言或者组织形式，很多时候还是对齐做的差，trigger / condition 不清楚，有时候原文都更管用了。

## P3. 用未来需求预测误差分别更新内容、状态和触发条件

- **要解决的问题**：记忆压缩不知道后面哪条信息会被用到；现在系统通常只改记忆内容，没有根据“预测会用却没用上”和“需要时却找不到”分别修正状态与触发条件。
- **假设**：从当前agent状态预测未来K步会用到哪些记忆，再把预测误差拆给内容、状态表示和触发条件三个更新器，能比只更新内容提高长任务中的记忆命中率。
- **做法**：先记录真实后续使用标签，训练一个轻量预测器；预测为需要但实际未用时修触发条件，需要时未召回的补内容或证据，状态表示则用未来使用分布和真实使用分布的差距更新。三个更新器分别做消融。
- **最小实验**：1–2周：选40条可回滚的长任务，记录每步真实取用的记忆；训练0.5B级的未来使用预测器，比较只更新内容、内容加触发条件、三者全开，使用同一模型和预算跑2个种子。
- **指标**：未来K步记忆使用排序AUC、必要记忆召回率、held-out成功率、平均注入token。
- **判负条件**：如果未来使用排序AUC低于0.6，或三者全开没有比只更新内容组提高至少2个百分点，就说明“记忆压缩本质是未来需求规划”在当前任务上不可操作。
- **风险 / 与已有工作**：“后来真的用上了”本身可能有噪声，容易退化成一次检索重排；预测状态论文只在较小合成任务上验证，不能直接外推到真实agent状态。
- **证据**：Recurrent Harness for Agentic Continual Learning · Failure Recovery via Belief Updates and World Modeling for Long-Horizon Agents · Generative sequence modeling for infinite memory processes via predictive states · Mosaic: Multi-Session Agentic Reinforcement Learning
- **来自你的灵感**：memory把原始信息压缩的问题就是你不知道后面到底哪块在啥时候就有用了，不记着就漏，都记着就乱。这其实是一种planning能力，如果能够判断未来所需。memory其实也是要基于未来预期与未来真实的gap来反馈更新的，只不过不光更新content/rule，也要更新state，trigger rational啥的

## P4. 把一两token造成的上下文翻转做成可预测的敏感度

- **要解决的问题**：同样是长上下文，改一个标点、一个小数或一个否定词，有时就足以让agent完成或崩掉；目前没有系统测量哪些上下文位置和token类型真正决定行为。
- **假设**：这种上下文敏感性能被少数结构化特征预测，尤其是目标、约束、工具名和历史证据中的语义关键token，预测器可以在运行前找出高风险上下文修改。
- **做法**：对同一任务的系统提示、目标、约束、工具schema和历史证据做一到三个token的受控替换，记录动作和最终成功率的变化；用编辑类型、句法角色、任务状态和模型概率训练敏感度排序器，并与编辑长度、词面重合度基线比较。
- **最小实验**：1–2周：从代码修复和文本agent各取150个任务，每类构造目标、约束、工具说明、历史复述四种单token或双token扰动；Qwen3-8B每组跑4个种子，再用一半任务训练敏感度排序器、一半留出评测。
- **指标**：行为翻转率、敏感度排序AUC、对高风险编辑的召回率、平均多消耗的rollout数。
- **判负条件**：如果受控扰动导致的显著行为翻转低于5%，或敏感度排序器无法超过简单的编辑长度和嵌入距离基线，就说明“小token改动”不足以成为独立研究方向。
- **风险 / 与已有工作**：容易得到描述性现象而没有因果机制；微小改动也可能只是把原任务改坏，需要同时报告是否仍保持语义和任务可解性。
- **证据**：Skip the Compressor: Coding Agents Fix More Issues When They Pick Whole Files · The Thinking Leakage in Reinforcement Learning for LLMs · Pack Light, CarryOn: Building Object-Oriented Context for Long-Horizon Agents · Sampling Reveals Style: Unsupervised, Training-Free Discovery of Prompt-Conditional Stylistic Axes in LLM Activations
- **来自你的灵感**：这种一两个token改变在上下文改变很多的其实值得系统性看看

## P5. 路由与控制器交给小决策模型，只对不可逆动作升级大模型

- **要解决的问题**：让大模型逐字决定下一工具或下一动作既慢又贵，而现有路由器通常只按置信度分流，不区分动作是否可以撤销。
- **假设**：小决策模型按动作选项输出分布，同时用“这个动作能否撤销”作为升级阈值，可以在接近大模型成功率的同时明显降低每任务成本，并减少不可逆错误。
- **做法**：在agent真实走过的状态上训练Jev式动作选择头；生成候选动作后，由本地小模型给选项概率，可逆的查询和编辑直接执行，不可逆的提交、删除、付款才调用大模型复核。训练集要包含小模型自己犯错后的状态，避免只学干净前缀。
- **最小实验**：1–2周：在τ²-bench的零售与电信子集上取200个任务，使用4B决策模型和同一个大模型复核器，比较全大模型控制、固定置信度阈值、可撤销性阈值三组；记录所有升级调用。
- **指标**：任务成功率、每任务大模型调用成本和延迟、不可逆动作错误率、升级率。
- **判负条件**：如果可撤销性阈值组没有至少节省20%成本，或成功率下降超过2个百分点，或不可逆错误率没有改善，就说明小决策模型不适合这个控制点。
- **风险 / 与已有工作**：JevAgentHarness已经证明真实状态训练和阈值拟合有用，新增点必须是“按可撤销性而不是单一置信度分流”；不可逆动作标注本身可能不可靠。
- **证据**：JevAgentHarness: Benchmarking, Deploying and Training Decision Models That Share Control with LLMs · StartLux-Decision: AutoThink Decision Models with Reinforcement Learning for Calibrated Deliberative Decisions · LEV: Thinking Fast and Deep with Looped Decision Models · ActionOPD: Distilling Decisions, Not Tokens
- **来自你的灵感**：现在jev as router或者controller感觉是个挺好的应用点

## P6. 把环境状态和期望分开，审计belief驱动的agent misalignment

- **要解决的问题**：模型对环境的判断会被自己的期望影响；同一个客观状态配上不同暗示，模型可能做出不同甚至越权的动作，而现有记忆只记录“发生了什么”，没有分离“观察到什么”和“以为会发生什么”。
- **假设**：显式维护环境事实、模型信念和期望来源，并用成对反事实任务约束动作选择，可以降低期望污染、错误记忆和越权动作。
- **做法**：状态写成“已观察事实、当前信念、期望来源、证据位置”四元组；构造观察完全相同但提示期望相反的成对任务。比较普通上下文、显式belief卡、belief预测辅助损失三种方案，并用内部探针检查模型是否把期望误当归一化事实。
- **最小实验**：1–2周：构造300个成对文本agent任务，一半改变观察、一半只改变期望暗示；在Qwen3-8B和一个小决策模型上比较普通历史、显式belief卡、belief卡加动作预测辅助目标。
- **指标**：客观任务成功率、同一观察下的动作一致性、belief-action一致性、越权动作率、错误事实写回率。
- **判负条件**：如果显式belief组在客观成功率或越权率上都不优于普通历史，或改变期望仍造成同样的动作偏移，就说明显式分离没有抓住问题。
- **风险 / 与已有工作**：内部状态探针依赖白盒模型，部署到API模型时不可用；显式belief字段也可能只是让模型更容易编理由，必须用可观察动作而不是自述内容验收。
- **证据**：Beyond Memory: Harnessing Long-Horizon Agents with Explicit Belief States · Failure Recovery via Belief Updates and World Modeling for Long-Horizon Agents · ANTE: Anticipate, Then Execute -- Learning Internal World Models for Coding Agents from Verified Beliefs · The Agent Knew: Internal States Forecast Unauthorized Actions and Stop Them, and the Lies That Follow
- **来自你的灵感**：说到belief，其实模型也有belief，其实这一块的misalignment也得考虑。因为有时候客观情况会被加期望影响，belief(env/state) ，也就是在xxx时出于yyy做了/认为zzz 这个case里的出于yyy的部分

## P7. 奖励能推翻前一步的有效反例，而不是泛泛分歧

- **要解决的问题**：只说答案对不对，模型学不到什么时候该撤回自己的结论；把“大家意见不一致”直接当奖励，又可能鼓励无意义争吵。
- **假设**：只有当一条反驳能生成可执行反例、改变验证器结果或推翻前一步证据时，才给额外奖励，能提高最终正确率和错误自纠率，而不会增加无根据的否定。
- **做法**：先让agent产出带证据的主张，再单独生成反例或反证；验证器检查反例能否真实跑挂程序或推翻前提，只有有效推翻才进入奖励，错误推翻要扣分。将“提出反例”“修正主张”“保持原答案”分开记录。
- **最小实验**：1–2周：收集200道带可执行校验的代码和逻辑题，比较只看最终对错、奖励普通分歧、奖励可验证反例三组；每组固定最多两轮修正，使用Qwen3-8B或同等模型。
- **指标**：最终正确率、经过验证的有效反例率、错误否定率、平均修正轮数、pass@k。
- **判负条件**：如果反例奖励组没有提高最终正确率，或错误否定率上升超过2个百分点，或收益只来自增加轮数，就说明这条奖励路线被推翻。
- **风险 / 与已有工作**：Beyond the Verdict已经证明反例比单纯判决更有信息，增量在于奖励“推翻已有主张”而不是只奖励判题；开放写作类任务没有可执行反例，不能直接外推。
- **证据**：Beyond the Verdict: Agentic Code Judging with Verifiable Feedback · SHELDON: Reasoning through Dual Search over Hypothesis and Observation Spaces · DiscoveryRSI: Recursively Learning to Discover Valuable Hypotheses · How AI Coders Discuss, Disagree, and Reach Consensus: Challenges and Opportunities for LLM-Based Qualitative Coding
- **来自你的灵感**：分歧和推翻，尤其是推翻，其实很重要 · 模型表达分歧，其实反而是一种好的reward，过于一致有时候才有问题。这个在测评中其实可以多考虑

## P8. 只在分歧能降低不确定性时奖励分歧

- **要解决的问题**：多agent一致未必正确，分歧也可能只是集体无能；仅按投票结果或意见不一致程度给奖励，无法区分“发现了新证据”和“多说了几句话”。
- **假设**：用可精确计算的后验分布衡量一条消息带来的信息增益，只奖励真正降低团队不确定性的分歧，能提高准确率和校准，同时抑制为分歧而分歧的刷分。
- **做法**：在可枚举隐藏状态的表格环境中，把共享信息、私有信息和答案概率全部显式化；每条消息计算其对正确答案后验的信息增益，只有增益为正才计奖励。比较最终答案奖励、原始分歧奖励和信息增益奖励，并单独监控一致性操纵。
- **最小实验**：1–2周：用4个agent、5个属性和可精确后验的隐藏状态任务训练Qwen3-4B决策头，比较结果奖励、按不一致度奖励、按信息增益奖励三组；另设无信息一致答案作为防合谋测试。
- **指标**：held-out正确率、每条消息的信息增益、校准误差、无根据分歧率、错误共识率。
- **判负条件**：如果信息增益组与结果奖励没有显著差异，或相对原始分歧奖励没有降低错误共识和校准误差，就说明分歧本身不能作为可靠奖励。
- **风险 / 与已有工作**：精确后验只在小规模表格任务中存在，真实工具任务的增益估计会很稀疏；如果用模型自估后验，可能把裁判偏差重新引入。
- **证据**：Training LLMs for Multi-Agent Collaboration with Verifiable Information Rewards · ProbabilityBench: Model Evaluation and Calibration with Exact Ground-Truth Uncertainty · How AI Coders Discuss, Disagree, and Reach Consensus: Challenges and Opportunities for LLM-Based Qualitative Coding · CLASHarness: Benchmarking Multi-Agent Conflict in Computer Use via a Controllable and Verifiable Generation Pipeline
- **来自你的灵感**：模型表达分歧，其实反而是一种好的reward，过于一致有时候才有问题。这个在测评中其实可以多考虑 · 分歧和推翻，尤其是推翻，其实很重要

## P9. 把OPD的信号质量拆成方向、幅度和额外信息

- **要解决的问题**：on-policy distillation经常只比较最终分数，无法判断学生到底学到了老师的正确方向、合适的更新强度，还是只吸收了老师多给的答案信息。
- **假设**：把每条蒸馏信号拆成方向一致性、幅度合理性和额外信息量三个可测分量后，可以比总KL或总损失更好地预测学生在新任务上的增益与遗忘。
- **做法**：在相同学生前缀上计算三个量：教师更新与目标能力方向的余弦、逐token概率调整的尺度、只有教师可见的额外信息带来的概率变化；用线性或小型回归器预测下游增益。比较总KL、交叉熵和三分量卡片。
- **最小实验**：1–2周：选数学与代码各50个任务，构造方向正确但缩放不同、方向错误但很强、额外信息很强三组教师信号；用Qwen3-4B学生做短步蒸馏，记录三个分量并拟合其与held-out增益的关系。
- **指标**：三分量对下游增益的排序相关性、held-out准确率、旧能力保持率、每提升1分所需训练token。
- **判负条件**：如果三分量模型不能比总KL或交叉熵更好地预测下游增益，或方向分量与最终收益没有稳定关系，就说明信号质量拆分没有实际预测价值。

## P10. 用用户意图当锚进化rubric基因组，不用模型短板自嗨

- **要解决的问题**：按当前模型最容易失败的题来扩展环境和奖励，会越来越迎合模型短板；但用户真正要的是需求被覆盖、结果可验收，而不是把模型不会的题刷到会。
- **假设**：把用户要求拆成可追踪的rubric基因组，并只允许在增加用户需求覆盖且通过冻结审计时才保留新条目，能比短板驱动课程获得更好的留出任务表现和更低奖励作弊。
- **做法**：基因组保存需求维度、依赖、反例和验证方式；每轮从用户任务说明和失败轨迹变异条目，但不能用测试集反馈直接选条目；由独立审计器检查覆盖、可执行性和冲突。比较固定rubric、模型短板采样和用户意图锚定三组。
- **最小实验**：1–2周：准备80个办公任务和3套用户偏好说明，比较固定rubric、按模型失败率出题、按用户需求覆盖出题；每轮用同一学生模型训练80步，另留30个未出现过的任务。
- **指标**：留出任务成功率、用户需求覆盖率、rubric误判率、奖励作弊率、每轮生成成本。
- **判负条件**：如果用户意图锚定组在留出任务和需求覆盖上都不优于短板驱动组，或为了覆盖而把误判率抬高超过3个百分点，就说明这个方向不划算。
- **风险 / 与已有工作**：“用户想要什么”可能无法完整形式化，rubric本身也会漏需求；必须防止用训练分布里的用户偏好反推考试答案。

## P11. 把state schema也放进harness自动搜索空间

- **要解决的问题**：harness自改进通常在改提示、工具和流程，agent究竟有哪些状态字段、何时写入状态往往由人写死，导致记忆和经验无法与新流程一起进化。
- **假设**：把状态字段、写入时机和记忆schema加入harness搜索空间，并在冻结留出集上验收，能比只改代码和提示获得更高的跨任务增益。
- **做法**：在Harness^2或RRSI式循环中加入schema编辑算子：增删状态字段、改变写入条件和压缩规则；每个候选都在同一任务上对照执行，只有留出集变好且没有泄漏才接受。单独记录状态字段带来的收益。
- **最小实验**：1–2周：选60个终端和文档任务，比较只搜提示代码与额外搜state schema两组，每组10–12轮、同token预算、3个留出任务集；使用一个中等规模开源模型。
- **指标**：留出集成功率、不同任务间迁移、schema复杂度、搜索token、开发集与留出集差距。
- **判负条件**：如果增加state schema搜索没有带来留出集提升，或只提升开发集并让留出集下降，就说明放开状态结构搜索不可行。
- **风险 / 与已有工作**：搜索空间会迅速膨胀，状态字段也可能变成泄题或记忆投毒入口；相对于RRSI，增量必须明确是“schema是搜索对象”而不是只改提示。

## P12. actor、critic、env同步进化，但验收器和审计集保持冻结

- **要解决的问题**：环境、判分器和执行策略一起自改进时，系统可能互相掩护，把奖励漏洞当成能力进步；现有工作多在改其中一层，缺少同步进化的低成本对照。
- **假设**：让actor、critic和env共享失败证据但各自更新，同时用冻结的独立审计集和不可改的权限边界验收，能在同算力下提高留出能力而不增加奖励钻空子。
- **做法**：actor按失败轨迹训练，critic学习预测后续成功与否，env按失败类型生成新环境；三者只共享公开证据，不共享最终测试答案。每轮先通过参考解和反泄漏检查，再由冻结审计器测能力、作弊和权限。比较固定环境、只改actor、三者共进化。
- **最小实验**：1–2周：搭100–150个可自动判分的终端短任务，跑三轮固定环境、actor-only和三者共进化；每轮同rollout和GPU预算，保留20个冻结审计任务和一组权限越界测试。
- **指标**：冻结留出集成功率、奖励作弊率、越权动作率、critic与真实结果一致率、每轮新增有效环境成本。
- **判负条件**：如果三者共进化没有比actor-only在留出集上提高，或冻结审计集的作弊率随轮次上升，就说明同步进化只是在互相掩护。
- **风险 / 与已有工作**：AutoEnvScaling和ClawLoop已经证明自动出题可行，增量必须有独立审计与权限边界；环境生成成本很容易超过收益。
- **证据**：AutoEnvScaling: Automating the Data Flywheel with Terminal Agents · ClawLoop: Self-Improving Agents via Harness-Native Training Loop · Self-Evolving Agent Harness · False Frontiers: Diagnosing and Mitigating Co-Cheating in Self-Evolving Search Agents
- **来自你的灵感**：就是得ACE一起RSI，actor，critic，env。小米那论文也是这个意思， · 其实还是infra提速+env+rubrics/reward，才是未来。

## P13. 迭代速度是不是RSI的乘数：做同算力延迟曲线

- **要解决的问题**：用户认为流程快和评测快是RSI关键，但“更快”可能只是节省墙钟时间，不一定提高单位算力产生的最终能力。
- **假设**：在总算力和数据相同的前提下，缩短单轮反馈延迟会提高能力随GPU小时的斜率；如果延迟只是工程优化，不同延迟组的能力-GPU小时曲线应基本重合。
- **做法**：固定同一组自生成任务和模型，只改变单轮反馈机制：同步等待全部rollout、流式边收边训、异步预取下一批评测。记录每6步的留出性能和累计GPU小时，避免把更多样本误当成更快。
- **最小实验**：1–2周：用120道可自动判分的终端题和Qwen3-4B，三档延迟各跑48个训练步、2个种子，每6步评测同一留出集，并记录累计GPU小时而不是只记墙钟。
- **指标**：能力-GPU小时曲线斜率、达到相同分数所需墙钟和rollout数、训练稳定性。
- **判负条件**：如果三组能力-GPU小时曲线在置信区间内基本重合，或加速只减少墙钟而单位算力增益不变，就说明迭代速度不是独立的RSI乘数。
- **风险 / 与已有工作**：延迟改造往往同时改变批大小、样本新鲜度和GPU利用率，必须做随机化对照；该实验只覆盖短终端任务，不能直接替代真实长程部署。
- **证据**：How to Measure RSI · Athanor: An Agent-Native System for Autonomous Post-Training Research · Score Centering Stabilizes Off-policy Reinforcement Learning · Mosaic: Multi-Session Agentic Reinforcement Learning
- **来自你的灵感**：流程做快和评测其实是RSI的关键，快速迭代+可验证的环境和反馈测试才能保证最终的scaling RSI。

## P14. 从任务原文和执行证据自动长出轨迹质检rubric

- **要解决的问题**：轨迹质检高度依赖人工，而普通LLM裁判只给整体好坏，难以指出哪一步违反了用户要求、哪一个文件差异能证明它做完了。
- **假设**：只从任务原文生成原子化rubric，再用日志、文件diff和可执行检查绑定证据，能比通用裁判更接近人工质检，并且更稳定地识别过程成功但结果未交付的情况。
- **做法**：为每个任务生成一组只包含单一主张的检查项，每项带证据来源和可接受/不可接受条件；裁判先定位证据再判分，能运行的条件交给工具。比较通用LLM裁判、成对比较和rubric加执行证据。
- **最小实验**：1–2周：从同一个agent基准抽240条成功与失败轨迹，人工标注200条作为评测锚点；比较整体LLM裁判、成对裁判、自动rubric裁判，所有裁判使用同一模型和工具权限。

- **判负条件**：如果自动rubric裁判相对通用裁判没有提高成功/失败AUC，或在人工锚点上涨分但证据引用正确率没有提高，就说明rubric没有真正解决轨迹质检。
- **风险 / 与已有工作**：rubric可能只奖励容易验证的字面要求，忽略用户真正意图；人类质检本身也有噪声，因此必须保留人工锚点和争议样本，而不是用模型重复自己的判断。

## P17. 置信度不是常数：用可信情境做条件校准而不是只报一个分数

- **要解决的问题**：模型报出的一个置信度会掩盖它只在某些任务、工具和上下文条件下才可靠；全局温度缩放无法告诉系统“这个0.8在这个场景里是否可信”。
- **假设**：按任务类型、工具可用性、上下文长度和歧义程度分层的条件校准，比全局校准更准确地预测错误，并能改善选择性执行和人工接管。
- **做法**：先记录条件特征和可验证的对错标签，训练分层校准器或保形预测器；比较全局温度缩放、单一ECE优化和条件化风险区间。只在风险低于阈值的条件下自动执行，其余交给复核。
- **最小实验**：1–2周：准备三套可自动判分任务，覆盖短问答、工具调用和长任务；在Qwen3-8B与一个决策模型上比较全局温度缩放、单层条件校准、分层保形校准，按任务族留出测试。
- **指标**：分层ECE、选择性预测的覆盖率-风险曲线、错误任务被人工接管的召回率、平均复核成本。
- **判负条件**：如果分层校准没有比全局校准降低分层ECE，或选择性执行在相同覆盖率下没有减少错误，就说明所谓条件置信度不能转化成可用信号。

## P18. HyperThink的涨分到底来自参数编辑还是提示条件

- **要解决的问题**：HyperThink看起来有趣，但需要分清收益是不是来自“按题生成一小块权重编辑”这一机制，而不是更长的提示、更多训练数据或普通LoRA适配。
- **假设**：HyperThink的主要增益来自题目条件触发的低维偏置/码本编辑，而不是提示模板本身；把编辑跨题交换或替换为随机编辑后，增益应明显消失。
- **做法**：复现偏置码本机制，设置提示模板控制、同参数量LoRA、零偏置、随机码本和跨题交换码本五组；用题目级因果干预检验生成编辑是否携带特定题目的计算信息，并在数学和代码任务上测迁移。
- **最小实验**：1–2周：在Qwen3-1.7B或同等模型上复现GSM8K训练、MATH-500留出，跑五组各3个种子；每组只改一题一次的偏置生成，不增加推理文本长度。
- **指标**：留出准确率、跨题码本交换后的准确率下降、编辑参数占模型比例、每个正确回答的FLOPs、分布外任务性能。
- **判负条件**：如果提示模板控制组与HyperThink相当，或跨题交换码本没有造成明显性能下降，或同参数量LoRA完全追平，就说明收益不是来自题目条件参数编辑。
- **风险 / 与已有工作**：作者的代码和正式实现未必可得，复现实验可能受训练配方影响；只能说明机制在该规模是否成立，不能直接否定更大模型上的效果。

## P19. 训练前预测一批合成数据会对学生模型带来多大提升

- **要解决的问题**：合成数据管线可以造很多题，但真正昂贵的部分是小规模试训和验证；如果能在生成后、全量训练前预测哪一批数据会提升下游能力，就能省掉大量无效实验。
- **假设**：结合难度分布、多样性、与基础模型的距离、验证器可靠性和错误类型覆盖，可以比数据量或随机抽样更准确地预测一批合成数据的下游增益。
- **做法**：先用少量候选批次做小步LoRA试训得到标签，再提取批次级特征；训练一个回归/排序模型预测留出任务增益，最后用未参与的批次验证。比较随机、数据量、难度和结构化特征四种选择器。
- **最小实验**：1–2周：针对一个小型代码或数学学生模型生成60个候选数据批次，每批做80步LoRA试训并记录留出增益；用三分之二批次训练预测器、三分之一批次测试选择效果。
- **指标**：预测增益与真实增益的Spearman相关、选择器相对随机选择的实际增益、浪费的试训GPU小时。
- **判负条件**：如果预测器与真实下游增益的Spearman相关低于0.2，或结构化预测选择没有比随机选择节省至少30%试训成本，就说明这个预测器不值得建设。
- **风险 / 与已有工作**：试训标签本身噪声大，且特征可能只对某个学生模型有效；若直接用测试集训练预测器，会变成另一种数据泄漏。
- **证据**：AutoSFT: An Agentic System for Automated Data Research in Supervised Fine-Tuning · SWE-at-Scale: Scalable Issue Synthesis from Historical Bug Fixes · Finetuning with Sampling: SFT Learns Better Than You Think · Scaling Verifiable Environments for Long-horizon Work Agents
- **来自你的灵感**：预测一些潜在影响，其实还是一种高级的数据分析，只不过这种预测数据对于训练结果的影响更有卖点

## P20. 把代码解题轨迹里的中间推理转成可规划的世界模型监督

- **要解决的问题**：很多agent轨迹只有最终动作和结果，没有显式表示“这个动作会让环境怎样变化”；如果能把代码推理过程中隐含的状态转移抽出来，可能训练出可用于多步规划的环境模型。
- **假设**：从代码或数学推理的中间步骤抽取“动作→下一状态”标签，训练的动作条件世界模型，会比只用最终成功轨迹训练的世界模型更能减少多步试错。
- **做法**：从仓库补丁、终端命令和解题CoT中抽取动作、观察、下一步状态三部分，构造状态转移数据集；训练一个小型动作条件预测器，在推理时只预测当前动作的状态变化并用于候选动作排序。比较无世界模型、普通轨迹世界模型和CoT增广世界模型。
- **最小实验**：1–2周：从100个代码和终端任务收集成功轨迹，抽取约2万条状态转移；用Qwen3-1.7B训练动作条件预测头，在50个留出任务上比较无世界模型、最终轨迹模型和CoT增广模型的动作排序与任务成功。
- **指标**：下一状态预测准确率、候选动作排序AUC、任务成功率、完成所需步数和工具调用数。
- **判负条件**：如果CoT增广世界模型没有比普通轨迹模型提高动作排序AUC，或提高预测准确率但不减少下游步数，就说明中间推理不能可靠转成规划监督。
- **风险 / 与已有工作**：MindAct目前只在灵感清单中出现，没有已归档论文证据；CoT中的状态描述可能只是事后合理化，和真实环境转移不一致。
- **证据**：From Traces to Agentic Worlds: Agentic Language World Models for Interactive Environment Simulation · ANTE: Anticipate, Then Execute -- Learning Internal World Models for Coding Agents from Verified Beliefs · Latent World Action Model for GUI Agents · RSI-Anything: Unlocking Recursive Self-Improvement with World Models

## P21. 先预测每步信用，再用后验回传核账

- **要解决的问题**：agentic RL的信用分配通常要等分支结束后才能回传，在线决策时不知道哪一步值得多采样、回溯或保留，导致算力平均浪费在所有步骤上。
- **假设**：仅凭当前状态和动作前缀就能预测每步后续功劳，预测信用与树回传的后验信用足够相关；用预测信用决定采样和保留能把预算集中到真正关键的步骤。
- **做法**：在可分支的工具任务中保留同一前缀的多条后续，用树回传得到后验信用作为标签；训练一个状态-动作信用预测器。在线时用预测信用决定是否分叉、是否回滚、是否送大模型复核，训练更新仍以实际后验为主，比较仅后验、预测加权奖励和预测预算分配。
- **最小实验**：1–2周：在50个可回滚的终端任务上用Qwen3-4B采8条分支，保留树结构并计算后验每步信用；训练信用预测器，比较GRPO、后验信用回传、预测信用分配三组，同采样预算、2个种子。
- **指标**：预测信用与后验信用的Spearman相关、单位GPU小时成功率、关键错误步骤召回率、训练方差。
- **判负条件**：如果预测信用与后验信用的相关性低于0.3，或预测分配没有比后验-only提高样本效率，就说明提前预测信用不能替代事后分支回传。
- **风险 / 与已有工作**：后验信用本身依赖分支环境和奖励设计，标签可能噪声很大；这里的增量不是重新设计信用公式，而是验证它能否被在线预测并用于预算分配。
- **证据**：Tree-Aware Posterior Distillation for Long-Horizon Agentic Reinforcement Learning · PACT: From Credit Assignment to Critic Alignment · ANTE: Anticipate, Then Execute -- Learning Internal World Models for Coding Agents from Verified Beliefs · FC-SWE: Failure-Conditioned RL for Long-Horizon Software Engineering Agents
- **来自你的灵感**：agentic RL里头，其实信用分配很重要，信用分配一般可以是后验的，其实可以考虑预测
